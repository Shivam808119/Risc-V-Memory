RISC-V MEMORY LAB

Writes, store buffers and memory traffic

A write changes state, so caches must define when the new value reaches lower levels and what another observer is allowed to see.

Two independent policy choices

Write policy questions are often confused. Write-through vs write-back answers when a store propagates to the next level. Write-allocate vs no-write-allocate answers what happens to the cache line on a store miss.

PolicyMeaningBenefits / costs
Write-throughUpdate cache and propagate write to lower level.Lower-level copy stays current, but more write traffic can occur.
Write-backUpdate cache; mark line dirty; write it down when evicted or required.Can reduce traffic, but needs dirty state and careful eviction/coherence handling.
Write-allocateOn store miss, fetch/allocate the line, then update it.Good if nearby bytes will be reused; can fetch data that is not needed.
No-write-allocateStore miss bypasses allocation in that cache.Avoids polluting cache for streaming writes, depending on system.

Store buffer

A store buffer holds stores after the execution unit produces them but before they fully drain to the cache/memory system. It can let later instructions continue while the memory side is busy. The core must still preserve the required ordering and forwarding behavior.

Store-to-load forwarding means a younger load can get bytes directly from an older buffered store when the addresses overlap appropriately, rather than waiting for the store to reach the cache. Partial overlaps and alignment make this logic subtle.

Write buffer vs store queue

These names vary by architecture. A write buffer often tracks writes waiting for a lower-level target. A store queue in a high-performance core can track speculative/retiring stores, check older stores against younger loads, and preserve ordering. Always use the particular manual/RTL's terminology.

Write combining and bursts

Several adjacent small writes may be merged into a wider transaction when the interface and memory type permit it. Bursts amortize address/control overhead across multiple data beats. These optimizations are not safe for every MMIO register; device semantics can require each write to remain distinct.

Atomics and fences

Atomic read-modify-write operations make an update indivisible with respect to the observers defined by the architecture and platform. RISC-V's A extension includes atomic operations; LR/SC is a load-reserved/store-conditional pair. A fence constrains the ordering of specified classes of memory and I/O operations. Neither concept should be confused with a cache flush: ordering and cache maintenance solve different problems.

MMIO caution: never assume that ordinary RAM caching/write-combining rules apply to device registers. A read can clear a status bit; a write can start a transfer. Use the platform's memory attributes and driver rules.
