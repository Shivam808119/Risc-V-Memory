NUMA, bandwidth and the Roofline model

These ideas are especially relevant to larger multicore systems and accelerators. They are useful performance tools, but not every small embedded core contains NUMA hardware or a DRAM cache hierarchy.

NUMA in plain language

NUMA means Non-Uniform Memory Access. In a NUMA machine, a processor can access memory attached to its own node more cheaply than memory attached to another node. “Non-uniform” means the cost depends on which processor and which memory location are involved.

CPU socket / node 0↔Local memory 0↔ interconnect ↔Remote memory 1↔CPU socket / node 1

NUMA is not just “a cache miss.” It is a system topology and placement property. Remote access may have higher latency, consume interconnect bandwidth and contend with other traffic.

When NUMA matters

  • Multi-socket servers or systems with multiple memory controllers/nodes.
  • Workloads that share data across CPUs or allocate memory far from the thread using it.
  • Operating-system scheduling and memory-placement policy.

A small FPGA soft core with a local block RAM normally does not need a NUMA explanation to describe its actual hardware. Mention NUMA only if the target system really has non-uniform memory domains.

Roofline model

The Roofline model compares a program's arithmetic work with how much data it must move. It estimates whether performance is limited mainly by compute throughput or memory bandwidth.

Arithmetic intensity = operations performed ÷ bytes transferred from the relevant memory level.
Bandwidth roof = peak memory bandwidth × arithmetic intensity.
Attainable performance is bounded by the lower of the compute peak and bandwidth roof, under the model's assumptions.

Example: a kernel performs 2 operations per byte and the memory system sustains 20 GB/s. The bandwidth roof is 40 billion operations/s. If peak compute is 100 billion operations/s, this kernel is likely bandwidth-bound in the simple model.

Compute-bound vs memory-bound

Compute-bound

The processor's arithmetic units limit progress. More bandwidth alone may not help.

Bandwidth-bound

The workload needs more data movement than the memory system can sustain. Better locality, reuse, compression or bandwidth can help.

Latency-bound

Dependent accesses wait for each result before requesting the next. More peak bandwidth may not help much; locality and latency hiding matter.

Why arithmetic intensity is not the whole story

Use bytes moved at the memory level you are analyzing, not simply source-code array size. Cache reuse can make DRAM traffic much smaller than L1 traffic. Store writebacks, prefetches, cache-line overfetch, coherence traffic and competing requesters alter the actual bytes transferred. Roofline is a model to guide investigation, not a guarantee of achieved speed.

How it connects to core designs

For SERV or PicoRV32, begin with instruction count, stalls, external memory latency and available bandwidth. For OoO BOOM, also study MLP, queues and cache behavior. NUMA is usually a platform-level question rather than a feature of the CPU pipeline itself. Roofline can be applied to any system if you have meaningful compute and bandwidth limits, but it is most common in high-performance computing and accelerator analysis.
