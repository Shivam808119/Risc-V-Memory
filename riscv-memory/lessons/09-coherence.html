RISC-V MEMORY LAB

Cache coherence, consistency, MESI and fences

Coherence answers which value a cache line represents when multiple agents cache the same location. Consistency answers which order of memory operations software is allowed to observe.

Why sharing creates a problem

Imagine two CPU cores each have a private cache and both read variable x. Core 0 writes a new value to its cached copy. Core 1 must not indefinitely read a stale copy if the platform promises coherent shared memory. Some mechanism must coordinate the copies.

Coherence

Cache coherence is usually discussed per memory location/cache line. It coordinates copies and writes so processors do not silently maintain incompatible versions. Common mechanisms include snooping (caches observe shared-bus transactions) and directory-based tracking (a directory records which caches hold a line). Small systems may have no hardware cache coherence at all.

MESI state names

StateMeaning, simplified
Modified (M)This cache has the only writable copy and it differs from lower-level memory.
Exclusive (E)This cache has the only clean copy; it can often become Modified without asking other caches.
Shared (S)Multiple caches may hold clean copies.
Invalid (I)This cache line is not a valid copy.

MESI is an example protocol, not a feature automatically present in every RISC-V core. A coherent interconnect or cache subsystem must implement the chosen protocol.

False sharing

False sharing occurs when different cores update different variables that happen to occupy the same cache line. The variables are logically independent, but the coherence protocol transfers ownership at line granularity. Padding or reorganizing data can reduce the effect.

Consistency / memory ordering

Memory consistency defines which orders of loads and stores may be observed by other harts and devices. RISC-V's memory model includes ordering rules and the FENCE instruction. The model can allow reordering that improves performance, while fences and atomic operations express required ordering.

Coherence and consistency are related but not interchangeable. A system can provide coherent caches and still allow memory operations to be observed in an order that surprises a programmer unless synchronization is used.

Simple litmus example

Initially: x = 0, y = 0
Hart 0:                 Hart 1:
  x = 1                  y = 1
  r0 = y                 r1 = x

Depending on the memory model and ordering constraints, can both r0 and r1 be zero? This is a classic way to test ordering assumptions. The answer must be derived from the specified model, instructions, fences and platform—not guessed from source-code line order alone.

Fences and atomics

FENCE orders selected predecessor and successor classes of memory and I/O operations. Atomic read-modify-write instructions provide indivisible updates and ordering semantics as specified. A lock algorithm usually needs both atomicity and ordering. A fence does not magically make a non-atomic increment indivisible.

Who needs coherence?

  • A single-core microcontroller with no caches may need no hardware cache-coherence protocol.
  • A multicore system with private caches and shared memory needs a coherent design or explicit software maintenance/ownership rules.
  • DMA devices can modify memory without using CPU caches; cache clean/invalidate rules may be required on non-coherent systems.
  • Directory/snoop mechanisms belong to the memory system/interconnect and integration, not to the RISC-V ISA alone.
Hart: RISC-V's term for a hardware thread of execution. A multicore or multithreaded system may contain multiple harts.
