Load/store, handshakes and memory buses

Learn the signals that make a request real: address, operation, data, byte enables, acceptance and response. These are the signals you will trace first in RTL.

Request, acceptance, response

A memory interface is not just an address wire. The two sides need to agree that a request is present, when it has been accepted, and when the response data is valid. Some simple protocols combine acceptance and response; others separate them.

Core raises request→Target accepts it→Target returns response→Core consumes result

Never assume signal names mean the same thing across protocols. In one interface, “ready” may complete a transaction. In another, a grant accepts the request and a separate response-valid signal arrives later.

Example: PicoRV32 native memory interface

PicoRV32's documented native port uses mem_valid and mem_ready, plus mem_addr, mem_wdata, mem_wstrb and mem_rdata. The core presents a request and keeps it stable until the peer signals readiness. A zero write strobe indicates a read; a nonzero strobe indicates a write. The native interface is simple and handles one transfer at a time; it does not, by itself, provide a cache.

if (mem_valid) begin
  // inspect mem_addr and mem_wstrb
  // read: mem_wstrb == 0
  // write: mem_wstrb != 0
  // completion: peer asserts mem_ready
end

Official starting point: PicoRV32 repository. Read the memory-interface section for exact cycle-level rules and the selected configuration.

Example: Ibex and CV32E40P style

Ibex separates request acceptance from the response: instruction-side signals include instr_req_o, instr_gnt_i, instr_rvalid_i and instr_rdata_i. CV32E40P documents OBI instruction and data interfaces. The important idea is the same: acceptance is not necessarily the same moment as returned data. This distinction allows the target to take time and the bus to define precise timing.

Handshake: a small agreement between two circuit blocks. For example, “I am presenting a request” plus “I accept it now.” The handshake prevents either side from guessing whether a transfer occurred.

Why byte strobes matter

A 32-bit data bus is 4 bytes wide. A byte store should modify only one byte, not overwrite all four. Four write-enable bits can represent which byte lanes are updated. This matters for C types like char, packed structures, unaligned byte fields and device registers.

Single outstanding vs multiple outstanding

A transaction is outstanding from the time it is accepted until its response completes. A simple interface may allow only one at a time. A higher-throughput design may allow several, often requiring transaction IDs or an ordering rule so responses are matched to requests. More outstanding work can hide latency, but adds queues, bookkeeping and verification complexity.

Bus protocols you may encounter

OBIOpen Bus Interface, used by CV32E40P and other embedded designs; read its exact version and implementation notes.
AXIAMBA protocol family with separate channels for address/control, data and responses; permits decoupled traffic.
WishboneAn open interconnect bus specification common in FPGA designs.
TileLinkA family of on-chip interconnect protocols used in the Rocket Chip ecosystem.
BridgeHardware that translates between protocols or widths.
ArbiterLogic that decides which requester gets a shared resource.
