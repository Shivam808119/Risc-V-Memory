CORE PROFILE

Ibex memory system profile

Small in-order RV32 core from lowRISC. Separate instruction-fetch and load/store paths; request/grant and response-valid concepts; optional instruction cache/integrity features depend on configuration and integration.

How to read this profile: verified general characteristics are separated from questions you must confirm for your exact build. Core-family capability is not proof that your configuration enables a feature.

What it is

Ibex is a small, configurable 32-bit RISC-V core maintained by lowRISC. Its documentation separates instruction fetch from the load/store unit, making it a strong example for learning the distinction between request acceptance and response arrival.

Instruction-side interface

Signals documented by Ibex include instr_req_o (request), instr_addr_o (address), instr_gnt_i (grant/acceptance), instr_rvalid_i (response data is valid), instr_rdata_i (data), and error/integrity signals. The request is held until accepted; response data may arrive later. This makes wait states and delayed memory responses explicit.

Data side / LSU

The load-store unit (LSU) generates data requests for load/store instructions. Read its protocol description for request/grant/response timing, byte enables, alignment behavior and error handling. Never assume a grant means the read data is already available: acceptance and response are conceptually separate events.

Cache and integrity caveat

Ibex configurations may include an instruction cache and optional integrity features, but these are configuration/integration choices. Verify the exact parameter set and top-level wrapper. A feature in the manual is not proof that a particular build enables it.

Study checklist

  • Trace the fetch interface to instruction memory or instruction cache.
  • Trace LSU requests to the data memory/interconnect.
  • Find how request grant differs from response-valid.
  • Check access-fault, integrity and alignment behavior.
  • Record whether the chosen build contains an I-cache and how it is invalidated/initialized.

Why these details matter

In a synchronous SRAM or interconnect, response latency can be multiple cycles. Separating grant and response makes the protocol able to model that latency without pretending that data arrived immediately. Error and integrity paths are also essential in systems that need robust fault reporting.
