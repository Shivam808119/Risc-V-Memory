RTL security review and verification lab

A repeatable method for turning security claims into evidence.

Start with a claim

Example: 'U-mode cannot write boot ROM.' Convert it into a testable property: for every U-mode store targeting the protected physical range, the request must be denied and no memory state changes.

Trace the path

Find instruction decode/CSR logic, protection checks, request generation, interconnect route, memory target and fault response. Check both instruction fetch and data access.

Directed tests

Test allowed and denied reads, writes and execution; region boundaries; overlapping regions; reset defaults; lock behavior; privilege transitions; debug states; malformed requests; bus timeouts and error responses.

Assertions

Use assertions to encode invariants such as: a denied request never commits a write; an alert remains asserted until acknowledged; a locked region does not change before reset. Adapt signal names and timing to the actual design.

Negative testing

Try invalid configurations, privilege changes, out-of-range addresses and interrupted boot/update flows. A passing happy-path test does not demonstrate isolation.

Evidence discipline

For each claim, save source file/line, commit hash, config, test name, expected result and observed result. Label items as verified, inferred or unknown.

Mini lab: protected region

Design a region that contains a secret or boot code. Write down which privilege level may read, write and execute it. Then test both allowed and forbidden accesses, including boundary addresses and instruction fetches.

// Pseudocode for a verification property
if (request_targets_protected_region && !authorized(request)) {
    assert(!write_commit);
    assert(access_fault_or_denial_reported);
}

This is conceptual pseudocode, not drop-in RTL. Adapt it to the real signals and timing of your design.
