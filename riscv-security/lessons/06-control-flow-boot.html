Secure boot, root of trust and firmware lifecycle

A system must establish trust before it can rely on its security software.

Root of trust

The smallest trusted component used to verify later stages. In hardware, this may involve immutable ROM, fused keys, lifecycle state and cryptographic verification. If the first stage is mutable and unverified, later checks can be bypassed.

Secure boot sequence

A typical chain: reset → immutable or protected first stage → verify next firmware image → measure or record relevant state → configure protection → transfer control. Exact chains vary; map the actual boot ROM and hand-off code.

Authentication vs encryption

Authentication verifies origin/integrity, often using a digital signature or MAC. Encryption protects confidentiality. Signed firmware can still be secret-free; encrypted firmware is not necessarily authentic unless authentication is also checked.

Rollback protection

A valid old firmware can contain known vulnerabilities. A monotonic version counter or protected rollback policy may prevent downgrade. It must resist reset, storage rollback and lifecycle manipulation.

Firmware update

Verify signature, version, target device, image length, metadata and failure behavior. Updates should be atomic or recoverable. Never erase the only working image before a replacement is verified.

Secrets and key storage

Keys should be provisioned and used in a controlled trust boundary. Avoid logging secrets, placing private keys in ordinary writable memory, or exposing them through debug, crash dumps or untrusted DMA.
