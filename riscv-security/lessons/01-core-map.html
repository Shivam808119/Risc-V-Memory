Start here: the ten cores

Before security analysis, understand what a core is, what the ISA specifies, and what belongs to the SoC. Security claims are only meaningful when tied to a specific implementation and configuration.

ISA vs core vs SoC

The ISA defines software-visible behavior and architectural rules. A core is the hardware implementation that executes instructions. The SoC includes the core plus memory, interconnect, peripherals, reset, boot ROM, debug and often security controllers. A secure ISA does not guarantee a secure product.

Why compare ten different cores?

The cores differ in size, pipeline style, configurability and intended use. A tiny microcontroller core may rely heavily on platform firewalls and firmware. A larger out-of-order core also requires attention to speculation, caches and transient state. The same threat-model checklist applies, but the likely failure modes differ.

The right unit of analysis

Record repository URL, exact commit/release, configuration file, top-level module, SoC/board, toolchain and firmware version. Without these, claims such as 'PMP is enabled' or 'debug is locked' cannot be reproduced.

A first mental model

Untrusted software issues instructions → the core checks architectural rules → requests travel through a bus/interconnect → memory/peripherals perform actions → faults and alerts return. Security can fail at any boundary.

Vocabulary you should already know

RTLRegister-transfer level: hardware described in Verilog/SystemVerilog/VHDL.
SoCSystem-on-chip: CPU plus memory, interconnect, peripherals and system control.
PrivilegeHardware-defined authority level controlling which operations/resources code may access.
ConfigurationParameters, plugins and integration choices that determine which features are present.
Threat modelExplicit statement of attacker capabilities, valuable assets and security goals.
Attack surfaceAll interfaces and behaviors an attacker may be able to influence.
