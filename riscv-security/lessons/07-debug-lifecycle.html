Debug, test, lifecycle and physical access

Debug access is powerful and useful, but it can bypass normal software isolation.

Why debug matters

Debug modules can halt a hart, inspect registers and memory, change execution, or interact with system buses. Those capabilities can defeat operating-system permissions if exposed to an attacker.

Authentication and disablement

Check whether debug access requires authentication, whether the policy is enforced in hardware, what happens in production lifecycle states, and whether reset or alternate straps reopen access. 'Disabled in firmware' is weaker than a hardware-enforced lifecycle policy.

JTAG and scan

JTAG and scan chains support test and manufacturing. Production devices need a controlled lifecycle transition that restricts invasive test features without preventing authorized servicing.

Reset and boot straps

Analyze reset defaults, strap sampling, brownout behavior and recovery modes. Security settings must default safely before firmware has executed.

Fault injection

Clock glitches, voltage changes, electromagnetic pulses or laser attacks may cause skipped checks or corrupted state. Physical countermeasures are product-specific; software redundancy alone may not be enough.

Secure failure

A detected fault should not silently continue with a privileged operation. Define whether the system halts, resets, raises an alert or enters a recovery mode, and verify that the response itself cannot be trivially suppressed.
