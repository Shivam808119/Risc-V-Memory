CORE PROFILE

SERV security profile

Security review guide for SERV: what the core is, which threat boundaries to investigate, and how to verify claims in the exact implementation.

What this profile can and cannot say: SERV is designed to minimize hardware area by processing datapath work serially. Security review should focus on the actual small RTL implementation, wrapper, bus fabric, reset/debug behavior and system-level protection. Do not assume the core provides PMP, MMU, cache isolation or cryptographic protection unless the selected RTL and integration prove it. This page is a research plan, not a certification or a claim that every listed security mechanism is present.

What is this core?

Bit-serial, area-minimal RV32 core. A core implements an ISA and microarchitecture; the surrounding SoC determines much of the real security posture. Keep those layers separate while researching.

What security should you investigate in SERV

RTL and platform boundary

Because SERV targets very small implementations, map which protections are implemented inside the core and which must come from the SoC. Small area does not imply insecure, but it often means the platform must provide many security services.

Privilege and memory checks

Search the exact RTL/configuration for privilege modes, CSR behavior, PMP or equivalent checks, and how denied accesses become traps. If absent, document that as an architectural limitation for the chosen build—not a universal claim about all SERV-based systems.

Bus and debug

Inspect every request path, address/data/strobe signal, debug/test access and reset defaults. Check whether non-CPU masters can reach the same RAM.

Practical evidence

Build a minimal test that attempts a protected write from the least-privileged mode supported by the selected system, then assert no write commits and a fault is reported.

Checklist: gather evidence

  • Exact repository, release tag or commit hash.
  • Top-level module and all security-relevant configuration parameters.
  • Supported privilege modes and CSR access checks.
  • Physical memory protection and/or virtual-memory translation, if any.
  • Instruction-fetch and load/store fault paths; whether denied operations have side effects.
  • Debug authentication, test interfaces, reset defaults and lifecycle behavior.
  • Bus/interconnect protection for every master, including DMA and accelerators.
  • Secure boot, firmware update and key provisioning in the complete platform.
  • Side-channel, integrity, fault-detection and alert behavior, with limits documented.
