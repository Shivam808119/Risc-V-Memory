CORE PROFILE

PicoRV32 security profile

Security review guide for PicoRV32: what the core is, which threat boundaries to investigate, and how to verify claims in the exact implementation.

What this profile can and cannot say: PicoRV32 is a compact configurable core with a simple native valid/ready memory interface. A security design must ensure that every address and byte strobe is checked by the memory system, that untrusted code cannot reach privileged regions, and that debug and reset access are handled by the platform. The native interface is not itself a security firewall. This page is a research plan, not a certification or a claim that every listed security mechanism is present.

What is this core?

Small configurable RV32 core. A core implements an ISA and microarchitecture; the surrounding SoC determines much of the real security posture. Keep those layers separate while researching.

What security should you investigate in PicoRV32

Memory interface is not an access-control policy

The native interface exposes address, write data, byte strobes and valid/ready handshake signals. These signals describe transactions; they do not by themselves decide whether the transaction is authorized.

Protect the external memory system

The wrapper or interconnect should validate the initiator, address range, operation type and byte enables before a transaction reaches a protected target. Check that instruction fetches and data accesses are both covered.

Privilege assumptions

Do not assume a general-purpose OS privilege architecture or PMP exists in a chosen PicoRV32 build. Verify the actual RTL and any wrapper/SoC protection. If all software executes with effectively unrestricted access, software separation is not a hardware security boundary.

Debug/reset/update

Review the selected wrapper, boot ROM, firmware update path and any external debug interface. Check reset values and whether the processor can execute unverified mutable code.

Checklist: gather evidence

  • Exact repository, release tag or commit hash.
  • Top-level module and all security-relevant configuration parameters.
  • Supported privilege modes and CSR access checks.
  • Physical memory protection and/or virtual-memory translation, if any.
  • Instruction-fetch and load/store fault paths; whether denied operations have side effects.
  • Debug authentication, test interfaces, reset defaults and lifecycle behavior.
  • Bus/interconnect protection for every master, including DMA and accelerators.
  • Secure boot, firmware update and key provisioning in the complete platform.
  • Side-channel, integrity, fault-detection and alert behavior, with limits documented.
