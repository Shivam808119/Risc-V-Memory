SonicBOOM / BOOM security profile

Security review guide for SonicBOOM / BOOM: what the core is, which threat boundaries to investigate, and how to verify claims in the exact implementation.

What this profile can and cannot say: BOOM is an out-of-order design commonly configured through Chipyard. Its speculative execution, branch prediction, load/store queue and cache hierarchy make transient-execution and side-channel analysis especially important. Mitigations and exposure depend on exact RTL/configuration, software, cache topology and SoC integration; do not label it vulnerable or safe without evidence. This page is a research plan, not a certification or a claim that every listed security mechanism is present.

What is this core?

Configurable out-of-order RV64 core family. A core implements an ISA and microarchitecture; the surrounding SoC determines much of the real security posture. Keep those layers separate while researching.

What security should you investigate in SonicBOOM / BOOM

Speculation is a first-class review area

BOOM is an out-of-order core family. Study branch prediction, speculative issue/retirement, load/store queue behavior, replay, exceptions and what microarchitectural state survives squashed instructions.

Architectural vs transient behavior

An instruction can be prevented from retiring architecturally yet still affect caches or predictors. Assess whether those effects can be observed under the actual cache and privilege configuration.

Isolation across contexts

Check cache sharing, address-space transitions, predictor state, SMT assumptions (if applicable to the exact system), and operating-system mitigation policy. Do not infer a vulnerability solely from out-of-order execution.

Configuration and mitigations

Use exact RTL, documented security advisories and tests. Avoid declaring the family 'safe' or 'vulnerable' without a reproducible attack model and evidence.

Checklist: gather evidence

  • Exact repository, release tag or commit hash.
  • Top-level module and all security-relevant configuration parameters.
  • Supported privilege modes and CSR access checks.
  • Physical memory protection and/or virtual-memory translation, if any.
  • Instruction-fetch and load/store fault paths; whether denied operations have side effects.
  • Debug authentication, test interfaces, reset defaults and lifecycle behavior.
  • Bus/interconnect protection for every master, including DMA and accelerators.
  • Secure boot, firmware update and key provisioning in the complete platform.
  • Side-channel, integrity, fault-detection and alert behavior, with limits documented.
